# AGENTS.md

FastAPI (SQLAlchemy/SQLite) + React/Vite/TS/Tailwind. Single Docker image; backend serves the built SPA when `SERVE_STATIC=true`. Deep references: `DEVELOPER.md`, `AI_GUIDE.md`, `AI_SETUP.md`.

## Commands

```
# Standalone local dev (Windows) — sets up venv/deps/.env on first run,
# launches backend + frontend each in their own window
.\start.ps1
.\stop.ps1

# Backend tests (from repo root, using the project venv)
./.venv/Scripts/python.exe -m pytest backend/tests -q      # Windows
.venv/bin/python -m pytest backend/tests -q                 # macOS/Linux

# Backend dev server
uvicorn backend.main:app --reload --port 8000   # run from repo root

# Frontend
cd frontend && npm run dev        # dev server, proxies /api to :8000
cd frontend && npm run typecheck  # tsc --noEmit
cd frontend && npm run build      # production build → frontend/dist

# Docker
docker compose up -d --build
```

## Architecture gotchas

- **Two JWT roles, two auth deps.** `core/deps.py::get_current_admin` / `get_current_tenant` are separate — never reuse one for the other's routes. Tenant-scoped routers (`routers/portal.py`) must read `tenant_user.tenant_id` from the verified token, **never** a client-supplied id.
- **Invoices are immutable snapshots.** `Invoice.room_rate`, `water_rate`, `water_divisor`, `monthly_rent`, `upi_id`, `payee_name`, `due_days` are copied from `Tenant`/`AppSettings` at creation time and never re-read live. `total_payable` is also immutable — write-offs are stored in the child table `invoice_writeoffs`, not subtracted from `total_payable`. Historical PDFs read only from the `Invoice` row, never `invoice.tenant.*`.
- **Net payable ≠ total payable.** `invoice_service.net_payable(invoice)` returns `max(total_payable − Σ writeoffs, 0)`. Always use this for "how much does the tenant owe" logic. `total_payable` is the original frozen amount.
- **Payments are an additive ledger, not a single field.** `invoice_payments` (`InvoicePayment`, child table like `invoice_writeoffs`) holds one row per payment received — `POST /api/invoices/{id}/payments` adds a row, it never overwrites one. `invoice_service.total_paid(invoice)` sums `invoice.payments`; `outstanding(invoice)` = `max(netPayable − total_paid, 0)`, `0` if `paid=True`. The old `invoices.amount_paid` column still exists (never dropped) but is write-only-by-migration now — nothing reads it at request time. `InvoiceOut.outstanding`/`totalPaid` are computed at serialisation, never stored. `previous_dues` auto-fill uses `outstanding`, not `net_payable`, so partially paid invoices carry forward only the unpaid remainder. A one-time guarded backfill in `migrate.py` (`_backfill_legacy_payments`) converts any pre-existing `amount_paid` value into an equivalent single payment row, guarded by "this invoice has zero payment rows" so it never double-inserts once real payments flow through the new table. Each payment has its own PDF receipt (`backend/templates/receipt.html`, `pdf_service.render_payment_receipt_pdf`) downloadable by both admin (`GET /api/invoices/{id}/payments/{pid}/receipt.pdf`) and the owning tenant (`GET /api/portal/invoices/{id}/payments/{pid}/receipt.pdf`, scoped through `_owned_invoice_or_404`). Only admin routes can add/delete a payment — the portal router has no mutation route for payments at all, by construction, not just by UI omission. **`add_payment` auto-marks `invoice.paid = True`** (and sets `paid_date` to the payment's own `paid_date`) when `amount >= owed` (the `outstanding` value computed *before* this payment was added — never re-read `invoice.payments` after `db.add()` in the same call without a refresh, since SQLAlchemy won't auto-sync an already-loaded relationship collection from a bare `invoice_id` FK write). This is forward-only: `delete_payment` never auto-unmarks `paid`, since an admin may have manually marked an invoice paid for reasons unrelated to the payment ledger.
- **Invoice creation gate.** `invoice_service.check_can_create_invoice` raises 422 if the last invoice has none of: `paid=True`, `amount_paid IS NOT NULL`, write-offs. Always called in `POST /api/invoices` before creating.
- **Portal access blocking.** `TenantUser.portal_access_blocked` (bool). When `True`: `tenant_login` returns 403 (not 401), and `get_current_tenant` returns 403 on every portal API call. Auto-set to `True` when `tenant_service.deactivate` is called (moved out). Toggle via `PATCH /api/tenants/{id}/portal-block`. The portal axios client (`portalClient.ts`) treats both 401 and 403 as "clear token + redirect to /portal/login".
- **Computed fields are server-only.** `InvoiceCreate`/`InvoiceUpdate` schemas don't declare `roomAmount`/`waterAmount`/`totalPayable`/rates at all — Pydantic drops them. All amounts come from `services/invoice_service.py::compute_invoice_amounts` (Decimal math, `ROUND_HALF_UP`, never float).
- **Write-off validation: amount must be > 0 and ≤ netPayable.** Enforced in `routers/invoices.py` before calling `invoice_service.create_writeoff`. Write-offs can only be added to unpaid invoices (also enforced server-side).
- **PDF generation degrades gracefully.** `services/pdf_service.py` guards the WeasyPrint import; if system libs are missing (common on native Windows), PDF endpoints return `501` instead of crashing the app.
- **Route ordering in `routers/tenants.py`.** `GET /{tenant_id}/documents/download-all` MUST be registered BEFORE `GET /{tenant_id}/documents/{document_id}/download` — FastAPI would otherwise match "download-all" as a `document_id` parameter. Similarly, `catchall_router` must always be last in `main.py`.
- **No Alembic.** New tables are created by `Base.metadata.create_all()` at boot. Changes to *existing* table columns go in `backend/migrate.py` as guarded `_add_column_if_missing` steps. Both run every boot — must stay idempotent. Do NOT add an early-return guard that skips migration when the DB file already exists — the guard was removed precisely because `create_all` already handles brand-new DBs and the `ALTER TABLE` steps are safe to re-run.
- **Password hashing uses `bcrypt` directly**, not passlib — passlib's bcrypt backend-detection breaks against bcrypt >=4.1. Don't reintroduce passlib.
- **Two visual sources of truth for the invoice**: `frontend/src/components/invoice/InvoiceDocument.tsx` (+ `invoice-print.css`) for on-screen, `backend/templates/invoice.html` for the PDF. Both carry "KEEP IN SYNC WITH" header comments — mirror layout/color/copy changes both ways.
- **Two independent frontend auth sessions** coexist in one browser via separate localStorage keys (`rentledger_admin_token`, `rentledger_tenant_token`) and separate axios instances (`api/adminClient.ts`, `api/portalClient.ts`). Don't merge them.
- **Profile photo storage** — stored as `uploads/tenants/{tenant_id}/profile_{uuid}{ext}`, path kept in `tenants.profile_photo_path`. Served via an authenticated `FileResponse` route (not a static mount). `TenantOut.hasProfilePhoto` is a boolean derived from this column.
- **Meter reading photos reuse `tenant_documents`.** They are regular `TenantDocument` rows with `doc_type="meter_reading"` and a non-null `invoice_id` FK. Up to 3 per invoice (enforced in `routers/invoices.py`). `InvoiceOut.meterPhotos` is populated by an explicit `db.query(TenantDocument).filter(TenantDocument.invoice_id == inv.id)` in `_out(inv, db)` — not via ORM eager loading. Both `routers/invoices.py` and `routers/portal.py` use the same `_out(inv, db=None)` pattern; all callers must pass `db`.
- **Integer display for meter readings** — `Numeric(10,2)` in the DB, but always whole numbers in practice. Display as integers: `| int` Jinja2 filter in `invoice.html`; `Math.floor(parseFloat(...))` in `InvoiceDocument.tsx`. DB columns are NOT changed — display-only.
- **Document visibility.** `tenant_documents.tenant_visible` (bool, default `False`). Only documents with `tenant_visible=True` and `doc_type != "meter_reading"` appear in the tenant portal (`GET /api/portal/me/documents`). Toggled per-document by the landlord via `PATCH /{tenant_id}/documents/{doc_id}/visibility`. `DocumentOut.tenantVisible` always present.
- **All UI strings go through `useLabels`.** `frontend/public/labels.properties` is the single source of truth for every user-visible string. Use `l('key', 'fallback')` in every component — never inline string literals in JSX. When adding a feature, append new keys to `labels.properties` first.
- **`MeterSubmission` status machine.** `pending → approved → applied` (tagged to an invoice) or `pending → rejected`. Once `applied`, `ms.applied_to_invoice_id` is set and the photo is excluded from the picker query (`status="approved" AND applied_to_invoice_id IS NULL`). Never transition directly from `pending` to `applied` — `approved` is a required intermediate state.
- **`save_meter_submission_as_document()` in `document_service.py`** creates a `TenantDocument` row (`doc_type="meter_reading"`, `invoice_id` set), marks the `MeterSubmission` as `status="applied"`, and sets `applied_to_invoice_id` — all in one commit. This keeps `MeterSubmission` as the review-queue staging table and `TenantDocument` as the invoice-attachment source of truth. Call it once per submission ID inside `POST /api/invoices` after the invoice is created; silently skip IDs that are invalid, already applied, or wrong tenant.
- **Portal write routes exist now.** `routers/portal.py` has `POST /api/portal/meter-submissions` (upload) and `GET /api/portal/meter-submissions` (list mine). Upload is rate-limited via `@limiter.limit("20/minute")` — the handler must have `request: Request` as its first param (slowapi requirement). `_VALID_PHOTO_TYPES = {"flat_meter", "water_meter", "property"}` is the allowlist.
- **Admin meter-submission review routes** live in `routers/tenants.py` under `/{tenant_id}/meter-submissions`. Route ordering: `GET /{ms_id}/photo` and `POST /{ms_id}/review` must not shadow each other; FastAPI resolves them by exact path match. The review endpoint raises 409 if `ms.status != "pending"`.
- **`meterSubmissionIds` on `InvoiceCreate`** is `list[str] = []` — optional, silently skips any ID that is not `status="approved"`, not belonging to the invoice's tenant, or already applied. No 422 on bad IDs; the invoice saves regardless.
- **Never read `err.response.data.detail` directly.** FastAPI returns it as a plain string for business-logic errors (400/403/404) but as an **array** of `{loc,msg,type}` objects on Pydantic validation failures (422) — rendering that array as a React child throws and (before the top-level `ErrorBoundary` existed) blanked the whole app. Always go through `errorMessage(err, fallback)` in `frontend/src/api/client.ts`, which normalizes both shapes to a string.
- **Top-level crash safety net.** `frontend/src/main.tsx` wraps `<App/>` in `components/ErrorBoundary.tsx` — an uncaught render error now shows a recoverable "Something went wrong" screen (and logs to console) instead of unmounting to blank white. All `localStorage` access goes through `lib/safeStorage.ts` (try/catch-wrapped) rather than calling `localStorage` directly, since some mobile/in-app browsers throw on storage access.
- **PWA service worker has no navigation fallback.** `frontend/vite.config.ts`'s `workbox.navigateFallback` is explicitly `undefined` — vite-plugin-pwa's default (`'index.html'`) binds a `NavigationRoute` that serves the precached app shell for every hard navigation, which can strand a browser on a stale, backend-incompatible build indefinitely after a redeploy. Don't re-enable it; this app always needs a live connection for its API calls, so there's no value in an offline app shell.
- **Hard-deleting a tenant (`DELETE /api/tenants/{id}`, distinct from `deactivate`'s soft-delete)** is `tenant_service.delete_tenant`. SQLite runs with `PRAGMA foreign_keys=ON` (`database.py`), and `Invoice`/`MeterSubmission`/`TenantDocument.invoice_id` have **no** cascade (`Tenant.invoices` is a plain relationship, `MeterSubmission` has no relationship to `Tenant` at all) — deleting a tenant with any of these raises `IntegrityError` unless rows referencing an invoice are removed *before* the invoice itself. Do it in this order: `MeterSubmission` rows → `TenantDocument` rows → `Invoice` objects individually via `db.delete()` (so `Invoice.writeoffs`' ORM cascade fires) → `db.delete(tenant)` (cascades `tenant_user`/`invites`). Files aren't touched per-row — everything under `{UPLOADS_DIR}/tenants/{tenant_id}/` is `shutil.rmtree`'d in one shot after the DB commit. Don't "simplify" this back to a naive `db.delete(tenant)`.
- **`PaymentProof` (payment screenshots) is invoice-scoped, not tenant-scoped.** Status flow mirrors `MeterSubmission`: `pending → approved → applied` (attached to a specific `InvoicePayment` via `applied_to_payment_id`) or `pending → rejected`. A tenant uploads from a specific invoice's page (`POST /api/portal/invoices/{invoice_id}/payment-proofs`), an admin reviews it on that same invoice's detail page, and `POST /api/invoices/{id}/payments` accepts an optional `paymentProofId` to attach an approved proof when recording the payment (`invoice_service.attach_payment_proof`, called from inside `add_payment`). `Invoice.payment_proofs` has ORM `cascade="all, delete-orphan"` — required, not optional: without it, deleting an invoice with any proof row raises `IntegrityError` under SQLite's `foreign_keys=ON`, same class of bug the tenant hard-delete work already hit for `Invoice`/`MeterSubmission`/`TenantDocument`. `delete_payment` must revert any attached proof (`status="approved"`, `applied_to_payment_id=None`) *before* deleting the `InvoicePayment` row, both to avoid the same FK violation and so the proof isn't stranded "applied" with no way to reattach it to a different payment. The receipt PDF embeds the proof photo (via `InvoicePayment.proof`, `pdf_service.render_payment_receipt_pdf`) only when `payment.proof.status == "applied"`.
- **Tenant portal-account recovery.** `PATCH /{tenant_id}/portal-account` doesn't exist — deletion is `DELETE /{tenant_id}/portal-account` (removes the `TenantUser` row, freeing the tenant to register again via a fresh invite — `TenantUser.tenant_id` is unique so re-registration is blocked while the row exists) and `POST /{tenant_id}/portal-account/reset-password` (generates and returns a random password once; never accepts an admin-supplied password, no email/SMS system exists to relay one otherwise). Both live in `routers/tenants.py` next to `portal-block`; UI is on the tenant's Invite tab (`InviteCodeCard.tsx`), only shown once `hasRegistered` is true.

## Conventions

- UUID primary keys as `String(36)`, `default=lambda: str(uuid.uuid4())` (SQLite has no native UUID type) — see every model in `backend/models/`.
- Routers stay thin; business logic lives in `backend/services/`.
- Frontend API calls go through `frontend/src/api/*.ts` modules, never inline `axios` calls in components.
- All money amounts are Decimal server-side, strings over the wire (Pydantic `Decimal` fields), parsed to `number` client-side only for display/preview math (`utils/formulas.ts`).
- Binary resources (images, PDFs, zips) are fetched via `fetchAuthedBlob(client, url)` in `utils/blob.ts` — plain `<img src>` / `<a href>` can't send the `Authorization` header.
- Full-size photo viewing uses `frontend/src/components/PhotoLightbox.tsx`, a generic click-to-enlarge overlay (Escape/backdrop-click/× to close) — reuse it for any thumbnail that already has a `fetchAuthedBlob` object-URL in state, rather than building another modal.
- **Update the relevant `.md` docs in the same commit as any behavior/architecture change** — new/changed endpoints go in `AI_GUIDE.md` §5, new gotchas go in this file's Architecture gotchas, PWA/Docker/security notes go in `DEVELOPER.md`. Don't push code changes with stale docs.
